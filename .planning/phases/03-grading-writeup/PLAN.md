# Phase 3 plan: grading, write-up, PR draft

**Status: not started.** Depends on the 120 run directories from Phase 2.

## Grading: three verdicts per run

Each is a boolean computed from the run directory. The grader is re-runnable offline; only "looks right" calls a model.

| Verdict | Definition | Source |
|---|---|---|
| `looks_right` | The run's code satisfies the task's written assertions, judged by an LLM reading the code. This is AssemblyAI's own method, reproduced on purpose. | `workspace/`, `tasks/<task>/rubric.json` |
| `runs` | The harness's execution of `./run.sh` exited 0 within the timeout and wrote an output file that validates against the task schema. | `contract.json`, `out.json` |
| `outcome` | The task's oracle passes on server-side evidence. | `server/`, `out.json`, `out.frames.jsonl` |

Rules:

- A run that hit a cap, or whose container failed, is `runs = false`, `outcome = false`. It stays in the denominator.
- For `looks_right`, fix the judge model and prompt before grading, grade every run twice, and report agreement. Hand-check a sample of 20 and report how often the judge was wrong.
- The streaming code-read check from Phase 2 (non-API parameter names in the source) is reported in its own table and is not part of `outcome`.

## The headline, defined before the data exists

**Silent failure** = `runs` is true and `outcome` is false.

Primary number: silent failures out of 40 runs, per condition, with a Wilson 95% interval (`twohundred/stats.py`). Also report it as a share of the runs that ran. Per-task breakdowns are labelled directional (n = 10).

Secondary: `looks_right`, `runs` and `outcome` pass rates by condition (chart 1); time and tokens to first working call by condition (chart 2), using the rule fixed in Phase 2 Q5.

## Pre-registered readings

Decide which is true from the numbers; do not steer toward one.

| If the data shows | Then the write-up says |
|---|---|
| Silent failures are common in `bare` and drop with the skill | The skill prevents N of M silent failures; here are the ones left and the server responses that would remove them. |
| The skill conditions have about zero silent failures | The skill closes the gap. These are the first execution-verified numbers for it, with intervals. |
| `bare` matches the skill on `outcome` once the agent can run code | The skill buys speed, not correctness; show the time and token difference and which guidance carried it. |
| Silent failures are rare everywhere | The quiet paths exist (Phase 1) but agents rarely land on them for these tasks. Say that plainly; the value is the harness and the matrix. |

"The API rejects loudly" was tested by the Phase 1 kill test and did not hold overall (4 of 10 loud).

Intervals at n = 40 are wide. If two conditions' intervals overlap, say the difference is not established.

## Failure taxonomy

Read every run where `runs` is true and `outcome` is false, and every `runs = false`. For each, record in `results/phase3/failures.csv`: what the agent sent, what the server did, whether a warning existed and where, whether the agent looked at it, and which Phase 1 probe (if any) it corresponds to. Group into a small set of named causes. The link back to Phase 1 probes is what turns the matrix from a list into a prediction.

## Write-up (D2)

`WRITEUP.md`, 600 words maximum, counted. For an engineer with three minutes.

1. First sentence: the headline number and what it means.
2. The probe matrix as the one table (by class and surface; link to `results/phase1/matrix.md` for rows).
3. Chart 1: three verdict pass rates by condition, with intervals. Chart 2: time and tokens to first working call by condition.
4. Method, in a short paragraph: tasks, conditions, n, what counts as outcome, the continuity re-grade, and one line citing Voice Standard Bench as the same principle (mechanical scoring against a known-correct result, no judge). Read the post first; the description here came from the owner.
5. Limitations, as a list: one agent, synthetic audio, n = 40 per condition, token-matched "names the fix", self-reported streaming frames if Phase 2 Q2 went with option A, web tools off, one account on one day.

Charts are generated by a script from `results/`, committed as SVG or PNG, and reproducible with one `make` target.
